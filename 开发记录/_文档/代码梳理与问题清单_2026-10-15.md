> 梳理人：Codex。范围：App 全量代码（Vue 渲染层 + Electron 主进程 + 拆解引擎接口）。
> 下面每条都标了**证据**（本机实测或代码位置），没验证的会写明"未实测"。

## 一、整体结构（先看这张图，后面加模块照着放）

```
运营电脑
├─ 界面（Vue 3 + Pinia）           src/
│   ├─ views/      直播间、弹幕、录制、拆解、设置、关于
│   └─ stores/     每个页面一个数据仓库，统一走 window.electronAPI
├─ 主进程（Electron/Node）          electron/
│   ├─ ipc-handlers.ts   所有前后端通道都在这儿注册（现在 25KB，偏大）
│   └─ services/         真正的业务逻辑，一个模块一个文件：
│       ├─ 弹幕：danmu-capture（隐身窗口+CDP 旁听）→ danmu.ts 解析 → database 入库
│       ├─ 录制：recording-manager → stream-recorder（ffmpeg 分段）+ disk-guard（磁盘）
│       ├─ 拆解：teardown（调引擎）+ teardown-queue（批量）+ packet-split（分片）
│       ├─ 对比：comparison（A/B 两场对齐）
│       ├─ AI：ai-analyze（直接调 DeepSeek）、ai-server+upnp（共享备用）
│       └─ 授权：license + signature（机器码/签名校验）
├─ 拆解引擎（Python，独立进程）      resources/engine/
│   直播拆解工具.py → index.py（索引）→ frames.py（网格图）→ transcript.py（转写）
└─ 数据位置  %APPDATA%\douyin-live-info\
    ├─ record.json / teardown.json / ai.json  （配置）
    ├─ 授权.json  danmu.db  logs\
```

**App 与引擎之间的契约**：App 传「视频文件或目录 + 模型名」，引擎在自己的 `work_<场次>` 目录里产出
`拆解素材包.md / manifest.json / index.md / grid_*.jpg / transcript.json`。App 再往里追加「第七节 弹幕与礼物」。
（建议把这条契约写成一页接口说明，以后换引擎实现不动 App。）

## 二、问题清单（按严重程度排序）

### P1【已修·2.4.8】批量拆解只拆第一段，超过 30 分钟的部分全丢

> **2026-10-15 已修复并实测**：`teardown-queue.ts` 里先 `await teardown.prepareInput()` 再拆。两段各 30 秒的测试场次，引擎日志已变成 `视频：…（无 _000）时长 1.0 分钟`，素材包正常生成。

- **现象**：一场录像被切成 `_000 / _001 / …` 多段时，「批量拆解」只分析 `_000`。
- **实测证据**（2026-10-15 本机）：造一场两段各 30 秒的录像入队批量拆解，引擎日志：
  `视频：测试主播_20260101000000_000.mp4　时长 0.5 分钟` —— 应该是合并后 1.0 分钟，也没有生成合并文件。
- **原因**：单场拆解在 `ipc-handlers.ts` 的 `teardown:start` 里先调 `teardown.prepareInput()`（合并分段）；
  而批量队列 `teardown-queue.ts` 直接 `teardown.start()`，跳过了合并。
- **影响**：分段设置是 30 分钟，所以**任何超过 30 分钟的场次，批量拆出来只有前 30 分钟**，
  不报错、看不出来，AI 复盘结论直接跑偏。
- **改法**：`teardown-queue.ts` 的 loop 里先 `await teardown.prepareInput(it.path)` 再 `start`；
  更稳的做法是把"合并"挪进 `teardown.start()` 内部，让所有入口都走同一条路。

### P2【已修·2.4.8】无口播/纯音乐的场次会整场拆解失败

> **2026-10-15 已修复并实测**：`transcript.py` 词级时间戳失败自动回退句级重跑。同一个会崩的素材，现在日志显示 `词级时间戳转写失败（…），改用句级时间戳重跑…` 后正常出素材包。

- **现象**：音频里没有可识别的人声时（纯音乐、唱歌无词、长时间静音段），转写脚本直接崩。
- **实测证据**：30 秒纯正弦音视频跑引擎 →
  `IndexError: boolean index did not match indexed array along axis 0 …`
  （位置：faster_whisper `add_word_timestamps` / `find_alignment`），引擎输出
  `转写失败（转写进程退出码 1）`，App 显示 `—— 结束（未生成素材包） ——`。
- **原因**：`transcript.py` 用了 `word_timestamps=True`，faster-whisper 在"这段没有词"时对齐会越界。
- **影响**：唱歌场、深夜静音场会整场报废；运营只能看到"转写失败"，无法自查。
- **改法**：转写循环包 try/except，失败自动用 `word_timestamps=False` 重跑一次；
  同时允许"0 句转写"也照样生成素材包（现在没素材包就等于没结果）。

### P3【已修·2.4.8】磁盘清理可能删掉"不是我们录的"文件，也可能删掉正在用的文件

> **2026-10-15 已修复并实测**：只删命名符合 `<主播>_<14位时间戳>_<分段号>` 的自家录像；正在录/正在拆的场次前缀受保护。实测：自家旧文件被删 ✅、同目录别人视频保留 ✅、刚改过的受保护文件保留 ✅。

- **证据**：`disk-guard.ts` 的 `enforceQuota()` 只按扩展名（.mp4/.ts/…）+ 修改时间从旧到新删；
  而当前录制目录是 `H:\迅雷下载`——里面混着迅雷下载的其他视频。
- **影响**：
  1. 目录一超 80GB，会从最老的开始删，**可能删掉你自己下载/放进去的素材**；
  2. 正在拆解的 `merged.ts`（读文件不更新修改时间）和"同场次早期分段"也可能被删，导致拆解中途失败。
- **改法**：只删符合我们命名规则的文件（`<主播>_<时间戳>_###`）并记清单；
  把"正在录制/正在拆解"的文件加入保护名单；默认输出目录建议改成专用子目录（如 `H:\迅雷下载\直播录像`）。

### P4【已修·2.4.9】弹幕历史/导出时间比实际早 8 小时

> 2026-10-15 修复：读取时统一 UTC→本机时间。实测历史列表显示 14:51:53（库内 UTC 06:51:53）。

- **证据**：库里存 UTC（实测最新行 `07:30` = 本地 `15:30`）；`DanmuView` 的历史列表、
  房间"最后活跃"、CSV/JSON 导出都直接用库里的字符串。
- **影响**：运营对不上"几点发生了什么"，和录像时间也对不上。
- **改法**：显示和导出统一转本地时间；或入库时就存本地时间+时区字段。

### P5【已修·2.4.9】弹幕库每 2 秒整库重写，且无限增长

> 2026-10-15 修复：保存改“临时文件+改名”原子写；RawData 截断到 2000 字；启动+每 6 小时清理 30 天前的数据并 VACUUM。实测注入 60 天前的旧消息，重启后自动清掉。

- **证据**：`database.ts` 用 sql.js（内存库），任何一条消息 2 秒防抖后把**整个数据库导出写盘**；
  现在 2800 行已经 7.6MB（原始 protobuf 全存了）。
- **影响**：热门房间消息量大时等于每 2 秒写几 MB～几十 MB；长期 7x24 会卡、吃盘；
  而且写盘是直接覆盖（没走"临时文件+改名"），断电/崩溃可能把库写坏。
- **改法**：RawData 压缩或按需存；定期清理 N 天前的数据；保存改原子写；量再大就换 better-sqlite3。

### P6【已修·2.4.9】崩溃/重启后不会自动恢复录制，也不清孤儿 ffmpeg

> 2026-10-15 修复：正在录的场次写入 record-state.json，启动 4 秒后自动恢复（6 小时内有效）；启动时清理命令行带 `-f segment` 的残留 ffmpeg。实测：开录→强杀→重启→自动接着录（5.5MB→11.8MB），合成孤儿进程被清掉。

- **证据**：`recording-manager.activeRoomIds()` 只被磁盘看门狗用到，
  没有"启动时恢复上次录制"的逻辑；ffmpeg 子进程没绑 job object，主进程崩了它会继续录。
- **影响**：7x24 最怕这个——半夜崩了/重启，第二天发现整晚没录；或孤儿 ffmpeg 把盘写满。
- **改法**：把正在录的房间持久化（record-state.json），启动时提示一键恢复；
  启动时清理上次残留的 ffmpeg（按镜像名+命令行匹配我们的输出目录）。

### P7【已修·2.4.9】AI 分析不能中止，中途失败前面的成果全丢

> 2026-10-15 修复：加 AbortController + “停止分析”按钮，每片跑完即落盘。实测：发起分析后 4 秒点停止，6 秒中止，报告带“没有跑完”标记。

- **证据**：`ai-analyze.ts` 顺序跑每一片，没有 AbortController，失败直接抛错、不写中间结果。
- **影响**：2 小时素材切 5 片，最坏跑 1 小时；想停只能关软件；第 4 片失败前 3 片白跑。
- **改法**：加"停止分析"按钮 + 每片跑完就落盘（断点续跑）。

### P8【已修·2.4.9】素材包超预算但"没有话术段"时不会拆分

> 2026-10-15 修复：新增按行兜底切分。实测 157k token 无话术包 → 切成 50 份，每份 ≤4000 token。

- **证据**：`packet-split.ts` 在找不到「逐句话术」或行数 < 2 时直接返回整包（`split=false`），
  即使总 token 已超上限。
- **影响**：这类场次喂给 AI 会超上下文（报错或被截断）。
- **改法**：兜底按章节/时间块均分。

### P9【已修·2.4.9】拆解页 AI 进度监听器每次进入都叠加

> 2026-10-15 修复：进入页面先 removeAiListeners() 再去重注册。

- **证据**：`TeardownView.vue` onMounted 里 `onAiProgress(...)`，onUnmounted 是空的。
- **影响**：反复切页回调越积越多（内存/CPU 微增）。
- **改法**：进入前先 `removeAiListeners()`。

### P10【已修·2.4.9】日志不轮转，时间戳是 UTC

> 2026-10-15 修复：日志用本机时间戳，只保留最近 14 天，并给 writeStream 挂 error 处理（磁盘满不再崩）。

- **证据**：`logger.ts` 每天一个文件但从不清理；时间戳用 `toISOString()`（日志里 08:18 对应本地 16:18）。
- **影响**：长期运行日志累积；排障时时间对不上。
- **改法**：保留最近 N 天 + 本地时间戳。

### P11【已修·2.4.9】遗留物清理

> 2026-10-15：signature.ts（已无人调用）删除；.bak 备份、__pycache__、旧安装包、dyhub 一并清理；旧版本共释放约 18GB。

- `signature.ts`（旧的直连弹幕签名）已无人调用；`danmu.ts.bak-*`、`transcript.py.bak*`、
  弹幕库里的测试表 `room_check5630…`。建议清掉，免得以后加模块改错文件。

### P12【已修·2.4.9】录像文件名用的是 UTC 时间

> 2026-10-15 修复：文件名改用本机时间。实测重启后自动恢复录制产生的文件为 `..._20261015184521_000.mp4`（18:45 本地）。

- 例：`青苔猫._20261015080405_000.mp4` 实际是本地 16:04 录的。运营按文件名找场次会懵。

### P13【提示·不是 bug】转写耗时

- 按内置对照表：small 约 17 分钟/小时素材；medium 约 60 分钟；large 约 150 分钟（CPU）。
- 运营机建议默认 small；想用显卡要先装 CUDA 运行库（装了才明显，不然自动回退 CPU）。

## 四、给"后面继续加功能模块"的建议

1. **通道集中但分文件**：`ipc-handlers.ts` 已 25KB，新模块别再往里堆；
   按 `registerXxxHandlers()` 拆成 `electron/handlers/xxx.ts`，主文件只做注册。
2. **配置加版本号**：record.json / teardown.json / ai.json 加 `schemaVersion` + 迁移函数，
   以后改字段不会让老电脑的配置炸掉。
3. **任务化**：拆解现在是全局单例状态（同时只能跑一场）。要支持"多场并行/远程提交"，
   得先把它改成"任务对象列表"。
4. **冒烟测试脚本化**：`_调试脚本/` 里已有 live-e2e、fresh-e2e、batch-merge-test 三个可复用脚本，
   建议每次发版前跑一遍（尤其 P1 改完后要有回归脚本盯着）。
5. **引擎接口文档**：把「输入/输出/文件命名/退出码约定」写成一页，App 和引擎解耦。
